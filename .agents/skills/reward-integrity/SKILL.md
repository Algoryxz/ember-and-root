# Reward Integrity Skill

## Purpose

Use this skill when implementing or reviewing any mutation that changes XP, Sparks, levels, streaks, branch XP, specialization, Trial state, inventory, or Sparks balance. Also use it when reviewing DB schema, RLS policies, or RPC functions.

No progression mutation is considered complete until failure cases are tested.

## Non-Negotiable Rules

These rules cannot be relaxed under time pressure or for convenience:

1. **Identity from server context only.** Every RPC derives `user_id` from `auth.uid()`. Never trust a caller-supplied user ID.
2. **Never trust client-supplied values** for XP, Sparks, level, price, or eligibility.
3. **All reward mutations are atomic.** A failure at any step rolls back all effects.
4. **Every mutation carries a `requestId` UUID.** Generated by the client before the call.
5. **Idempotency via `mutation_receipts`.** Check before executing; store result after.
6. **Same `requestId` + same payload → replay prior result** (no duplicate reward).
7. **Same `requestId` + different payload → reject** (misuse detection).
8. **`quest_completions` and `currency_ledger` are immutable.** No UPDATE or DELETE.
9. **Direct browser writes to progression tables are denied by RLS.** Verify this for every new table.
10. **Service-role key is never in client bundle.** Used in seed/migration scripts only.

## Mutation Implementation Checklist

Apply this checklist to every new or changed RPC function:

### Authentication
- [ ] RPC uses `SECURITY DEFINER`
- [ ] `user_id` derived from `auth.uid()` at the start of the function
- [ ] No caller-supplied `user_id` parameter accepted

### Ownership
- [ ] If operating on a quest: `SELECT ... WHERE id = $quest_id AND user_id = auth.uid()`
- [ ] If operating on an inventory item: same ownership check
- [ ] If operating on a branch or trial: implicitly owned by `auth.uid()`

### Input validation
- [ ] All text inputs trimmed and length-constrained
- [ ] Enum values validated against CHECK constraint or explicit check
- [ ] Numeric values have non-negative checks where applicable

### Concurrency control
- [ ] Profile row locked with `SELECT ... FOR UPDATE` before reading or mutating XP/balance/streak
- [ ] For quest edits: `version` column checked for optimistic concurrency

### Idempotency
- [ ] `mutation_receipts` checked at the start: `SELECT ... WHERE user_id = auth.uid() AND request_id = $request_id`
- [ ] If receipt found with same `payload_hash`: return stored `result_event` immediately
- [ ] If receipt found with different `payload_hash`: raise error `'request_id_reuse'`
- [ ] Receipt inserted at the end of the transaction with `result_event`

### Daily cap (quest completion only)
- [ ] `daily_xp_awarded` computed from `SUM(xp_awarded) WHERE user_id = auth.uid() AND local_date = current_local_date`
- [ ] `awarded_xp = LEAST(base_xp, GREATEST(0, 140 - daily_xp_awarded))`
- [ ] `sparks_awarded = awarded_xp / 5`
- [ ] Cap hit is reflected in `MutationResult.event.cappedToday`

### Transaction completeness
- [ ] `quest_completions` inserted (immutable)
- [ ] `profiles.total_xp` incremented
- [ ] `profiles.sparks_balance` incremented
- [ ] `branches` row upserted with attribute XP increment
- [ ] `currency_ledger` row inserted (immutable)
- [ ] Streak and `last_activity_date` updated
- [ ] `profiles.revision` incremented
- [ ] `mutation_receipts` inserted
- [ ] All above in one `BEGIN ... COMMIT` block

### Result
- [ ] Returns `MutationResult` JSON with `revision`, `event`, and `snapshot`
- [ ] `event` includes `previousLevel` and `newLevel` if level changed
- [ ] `event.specializationAvailable = true` if branch XP just crossed 80
- [ ] `event.emberRelit = true` if first completion after a missed day
- [ ] `snapshot` is a fresh `GameSnapshot` reflecting committed state

### Failure handling
- [ ] Any exception triggers `ROLLBACK` (let PostgreSQL handle this)
- [ ] No partial reward is ever visible after a failed transaction
- [ ] Error messages are non-leaking (no internal stack traces to client)

## Trial Integrity Checklist

For `startTrial` and `claimTrial`:

- [ ] Specialization has been chosen for this attribute before starting Trial
- [ ] `startTrial`: creates row only if none exists for `(user_id, attribute)` (unique constraint)
- [ ] Evidence counting uses only completions `WHERE completed_at > trials.started_at`
- [ ] Evidence counting ignores pre-start completions
- [ ] Distinct-day count uses `COUNT(DISTINCT local_date)` from `quest_completions` for this attribute after Trial start
- [ ] `claimTrial`: validates evidence condition fully before setting `claimed_at`
- [ ] Double claim attempt: returns existing result (idempotent via receipt)
- [ ] Crest availability: `branches.xp >= 160 AND trials.claimed_at IS NOT NULL`

---

## Purchase Integrity Checklist

For `purchaseItem` and `equipItem`:

- [ ] Balance check: `profiles.sparks_balance >= items.price` (server-side)
- [ ] Already-owned check: `NOT EXISTS (SELECT 1 FROM inventory WHERE user_id = auth.uid() AND item_id = $item_id)`
- [ ] Debit: `profiles.sparks_balance -= items.price`
- [ ] Ledger: insert negative-amount row in `currency_ledger`
- [ ] Inventory: insert row (primary key `(user_id, item_id)` prevents duplicates)
- [ ] `equipItem`: set `equipped = true` on target, set `equipped = false` on all others (partial unique index prevents two equipped)
- [ ] `equipItem`: verify item is owned before equipping

## High-Value Test Cases

Every backend change must maintain passing tests for:

| Test | Verified by |
|------|-------------|
| Unauthenticated mutation rejected | Supabase RLS; Playwright test |
| User B cannot read user A's rows | RLS; two-account Playwright test |
| Double-click / retry awards XP exactly once | Vitest idempotency test |
| Simultaneous completions respect daily 140 XP cap | Vitest concurrency test |
| XP below/at/above level threshold produces correct level | Vitest boundary test |
| Forced mid-transaction failure leaves no partial reward | Vitest rollback test |
| Same local date: streak unchanged | Vitest streak test |
| Next local date: streak incremented | Vitest streak test |
| Missed day: streak resets to 1, longest preserved | Vitest streak test |
| Insufficient balance purchase: error, balance unchanged | Vitest economy test |
| Already-owned purchase: error | Vitest economy test |
| Trial evidence ignores pre-start completions | Vitest trial test |
| Trial distinct-day count uses correct date window | Vitest trial test |
| Claim Trial twice: idempotent | Vitest idempotency test |

## RLS Verification Checklist

For every new or modified table:

- [ ] RLS enabled: `ALTER TABLE table_name ENABLE ROW LEVEL SECURITY;`
- [ ] Default deny: no `USING (true)` policy
- [ ] Read policy: `USING (user_id = auth.uid())`
- [ ] No direct `INSERT`/`UPDATE`/`DELETE` from `authenticated` role on progression tables
- [ ] `items` table: readable by `authenticated`, no user writes
- [ ] Verified with a signed-out request (should return nothing)
- [ ] Verified with two accounts (user B cannot see user A's rows)

## Acceptance Output

When you complete a backend task using this skill, report:

1. **Transaction boundary** — which tables are locked and mutated in the same `BEGIN...COMMIT`
2. **Constraints used** — which SQL CHECK constraints, UNIQUE constraints, and FK constraints prevent invalid state
3. **Idempotency path** — which receipt key is used and what replay returns
4. **Tests run** — list each test and its result (pass/fail)
5. **Residual integrity risk** — any known gaps or edge cases not yet covered by tests
